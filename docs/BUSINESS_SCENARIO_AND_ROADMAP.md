# 业务场景与迭代路线

更新日期：2026-08-28。

## 1. 当前业务定位

本系统当前定位为面向住宅、老旧小区和出租屋的火灾风险监测与联动处置演示平台。主要用户是物业/社区安全管理员、消防巡查人员和值班人员；设备端负责采集数据，Web 管理大屏负责集中监控和处置，钉钉负责把告警与广播送达值班人员手机。

当前版本适合功能演示、毕业设计验收和小范围试点验证，尚不等同于经过消防认证的火灾自动报警系统，也不应替代法定消防设施、人工巡检和应急报警流程。MQ-2 更适合判断“是否出现烟雾/可燃气体及变化趋势”，系统中的 ppm 是近似估算值，不是实验室级绝对浓度。

## 2. 参与角色

| 角色 | 登录后界面 | 主要职责 |
| --- | --- | --- |
| 系统管理员 | 系统总览、3D 社区、设备/通知/广播/用户管理 | 管理账号、权限、设备、地图位置和系统配置 |
| 小区管理员 | 小区监控、3D 社区、设备/通知/广播管理 | 维护设备位置，处置告警和组织日常安全管理 |
| 消防员 | 应急总览、3D 态势、告警通知和应急广播 | 快速定位火情、处置告警并组织疏散 |
| 居民 | 我的安全、只读 3D 社区和安全问答 | 查看社区安全状态，不执行管理操作 |
| 传感设备 | 无 Web 账号 | 通过 HTTP 或 MQTT 上报心跳、烟雾、温湿度、电流、线缆温度和 CO 数据 |

## 3. 当前业务闭环

1. 设备通过 HTTP 或华为云 IoTDA MQTT 上报遥测数据，后端完成幂等处理、数据入库和在线状态刷新。
2. 3D 地图根据数据库中的楼栋、楼层、房间和设备坐标显示空间位置，并叠加在线、离线和告警状态。
3. 规则引擎对六类传感器指标执行预警/危险判断，设备离线由定时任务单独判断。
4. 首次进入告警范围时创建活动告警，并写入站内 APP、SMS 和钉钉通知记录；其中钉钉为真实单聊下发，APP 是站内通知记录，SMS 尚未接入供应商。
5. 同一设备、同一指标、同一严重级别的活动告警不重复轰炸；由预警升级为危险时再次发送钉钉消息。
6. 管理员或消防员在 Web 端通过 3D 空间定位确认、辅助复核、解决或标记误报，系统保留处理人与通知投递记录。
7. 有权限人员可创建广播并下发到全部已绑定员工的钉钉单聊，也可再次下发或删除广播记录；删除记录不会撤回已经送达钉钉的消息。

## 4. 当前告警口径

危险规则优先于预警规则。下表中未覆盖的中间区间只进入趋势观察，不自动生成告警。例如温度 31–45℃、CO 11–49 ppm 本身不触发告警。

| 指标 | 参考正常范围 | 预警 | 危险 |
| --- | --- | --- | --- |
| 烟雾浓度 | `< 100 ppm` | `100–300 ppm` | `> 300 ppm` |
| 环境温度 | `20–30℃` | `> 45℃`，或 5 分钟内升温 `>= 10℃` | `> 60℃` |
| 环境湿度 | `40–70%` | 5 分钟内下降 `>= 20` 个百分点 | `< 20%` |
| 电气电流 | `0.5–5A` | `> 10A`，或 5 分钟内波动 `>= 5A` | `> 15A` |
| 线缆温度 | `< 50℃` | `> 70℃` | `> 90℃` |
| 一氧化碳 | `0–10 ppm` | `50–100 ppm` | `> 100 ppm` |

当前烟雾阈值固定为 100 ppm，不允许通过设备编辑页面改成其他数值，以保持告警口径一致。后续如需按房型、设备标定结果或监管要求配置阈值，应改为“规则模板 + 审批 + 版本记录”，而不是直接开放任意输入。

## 5. 当前部署场景

| 组件 | 当前地址/方式 | 说明 |
| --- | --- | --- |
| Web 前端 | `https://easterproject.pages.dev` | Cloudflare Pages，跟随 GitHub `master` 构建 |
| 公网 API | `https://api.kangroom.eu.cc` | Cloudflare Named Tunnel 固定域名 |
| 本地 API | `http://127.0.0.1:8080` | Spring Boot 在开发者电脑运行 |
| 数据库 | 本机 MySQL `smart_smoke` | 电脑关机或 MySQL 停止后不可用 |
| 手机消息 | 钉钉 Stream + 机器人单聊 | 员工首次私聊机器人后自动绑定为接收人 |

Named Tunnel 重启后不需要修改后端域名或重新配置 Pages；但本机后端、MySQL 和 `cloudflared` 都必须持续运行。固定域名只解决地址稳定性，不提供 7×24 小时可用性。

## 6. 后续迭代方案

### P0：稳定演示版（建议 1–2 周）

- 增加住宅、阴燃、电气过载和快速火灾四套可重复的数据模拟场景，可选择设备、倍率和持续时间。
- 在现有 3D 地图上增加火情扩散动画、楼层剖面和场景模拟联动，不改变真实告警记录的审计语义。
- 为后端、MySQL 和 Named Tunnel 增加一键启动、启动前检查、进程守护及清晰日志。
- 增加告警恢复判定、迟滞区间和冷却时间，减少临界值抖动；保留当前预警升级危险机制。
- 完成钉钉失败重试、接收人启停和投递失败可视化；补充端到端自动化测试。
- 验收标准：四种模拟场景可重复触发预期告警；同级不重复、升级会再通知；重启后固定域名无需修改。

### P1：小区试点版（建议 2–4 周）

- 接入少量真实设备，记录 MQ-2 预热、基线、原始 ADC/电阻比和标定参数，不只保存近似 ppm。
- 建立“小区—楼栋—单元—房间—设备”层级，以及值班班组、责任人和告警升级策略。
- 钉钉消息增加结构化告警卡片、现场确认入口和超时升级；必要时接入短信作为兜底通道。
- 完成 MQTT 下行：蜂鸣器/声光报警控制、设备回执、超时重试和指令审计。
- 验收标准：真实设备连续运行并具备离线监控；每条告警可定位到房间、责任人和完整处置记录。

### P2：生产化部署（建议 1–2 个月）

- 将 Spring Boot 与 MySQL 迁移到长期运行的云服务器或托管平台，设置 TLS、WAF、最小权限数据库账号和机密管理。
- 引入进程/容器健康管理、监控指标、日志集中采集、每日备份和定期恢复演练。
- 使用 Flyway/Liquibase 管理数据库版本；使用 Redis 或网关实现多实例共享限流和会话安全状态。
- 使用 SSE/WebSocket 替代主要页面的 3 秒轮询，并实现告警投递队列、重试、幂等和死信处理。
- 验收标准：完成故障、断网、重启和备份恢复演练；关键接口、告警延迟与通知成功率可监控。

### P3：产品化扩展（按业务优先级）

- 接入摄像头和可解释的视觉复核，但模型结论仅作为辅助证据，不自动替代人工确认。
- 增加地图/楼层图、设备巡检、传感器寿命、校准记录、风险评分和趋势报表。
- 建立规则模板、版本审批、灰度发布和不同场所策略，支持多租户与数据隔离。
- 对接物业工单、消防值班流程或其他企业协作平台，形成跨系统事件闭环。

## 7. 推荐的下一步

优先实施 P0 的“场景模拟器 + 告警恢复/迟滞 + 服务一键守护”。这三项能直接提升当前演示的稳定性和可重复性，也能为真实硬件试点提供可靠基线。真实设备标定和云端生产化应在演示闭环稳定后进入 P1/P2，避免过早扩大部署复杂度。
